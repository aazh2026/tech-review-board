# 技术评审与决策管理平台 · 功能设计说明书 (Functional Design Document)

**文档版本**：v2.0 (精简易用与全流程贯通版)  
**治理模式**：模式 C · 分级授权管理 (三级 DRB 架构体系)  
**面向对象**：架构师、DRB 委员、组织秘书、技术委员会主席、工程研发人员

---

## 一、平台背景与设计目标

### 1.1 建设背景
在现代化多产品族、跨云原生与 AI 复杂工程背景下，大型企业面临技术选型无序膨胀、架构债务堆积、生产故障溯源难、评审形式化等痛点。  
平台基于 **“模式 C：分级授权管理”**，实现：
- 集团集中定规范、定原则、定红线；
- 产品族自治执行，在授权边界内完成自主决策；
- 发生重大争议、突破红线或跨产品族影响时，平滑升级至集团最高委员会；
- 杜绝“边审边改”的不确定性，确立不可篡改的材料快照与严格整改闭环。

### 1.2 核心设计原则
1. **三权分立**：专业质询权（专家）≠ 民主表决权（委员）≠ 授权签发权（主席）。
2. **材料冻结 (BR-017)**：正式开会前材料必须快照锁定并生成 SHA-256 签名，未冻结材料不得启动评审。
3. **双 2/3 法定表决 (BR-022)**：表决须实到人数 ≥ 2/3，赞成票（含附条件）比例 ≥ 67% 方为表决通过。
4. **决策权威与版本化 (BR-026 & BR-027)**：决策人独立裁决；决策已发布后严禁无痕修改，必须通过新版本号（V1.1、V2.0）增量修订发布。
5. **独立核验闭环 (BR-033 & BR-037)**：整改人不得自我验收；未完成独立核验的 P0/P1 缺陷硬阻断议题关闭。

## 二、组织架构与权限体系

### 2.1 三级 DRB 组织架构 (Hierarchy)
- **L1 企业级技术评审委员会 (EDRB / Group DRB)**：
  - 管辖范围：跨产品族依赖、企业级技术战略演进、技术例外审批、重大资损事故。
  - 主席：集团首席架构师 / 技术委员会主任。
- **L2 产品族技术评审委员会 (Family DRB)**：
  - 管辖范围：单产品族内各系统架构设计、中台 API 演进、重要技术选型。
  - 主席：产品族首席架构师；秘书：专职架构治理专家。
- **L3 产品级架构评审组 (Product Architecture Review Team)**：
  - 管辖范围：单模块技术设计方案、局部重构、数据库表结构与索引设计。
- **横向专项专家组 (Horizontal Committees)**：
  - 信息安全委员会（负责安全合规、凭证 TTL、数据防泄漏审查）；
  - 稳定性与可靠性委员会（负责容灾多活、限流熔断、压测审查）。

## 三、议题全生命周期状态机 (Lifecycle State Machine)

平台定义了严密的议题流转状态机：

```
[DRAFT 草稿]
    │ 提交申报
    ▼
[PENDING_ACCEPTANCE 待受理] ──(形式审查退回)──> [DRAFT]
    │ 形式审查通过
    ▼
[PREPARING 准备中/待冻结]
    │ 材料快照锁定 (BR-017)
    ▼
[REVIEWING 评审审议中] ──(会中争议/超范围)──> [ESCALATED 跨级升级]
    │ 委员投票表决 (BR-022)
    ▼
[DECISION_PENDING 待决策]
    │ 主席签署正式决策书 (BR-026)
    ├─────────────────────────────┬────────────────────────────┐
    ▼                             ▼                            ▼
[PASSED 通过]             [CONDITIONAL_PASS 附条件通过]   [REJECTED 否决驳回]
    │                             │
    │                             ▼
    │                     [REMEDIATING 整改中]
    │                             │ 提交整改代码PR与方案
    │                             ▼
    │                     [VERIFYING 待独立核验]
    │                             │ 独立专家审核通过 (BR-033)
    │                             ▼
    │                     [VERIFIED 整改已核验]
    │                             │
    └─────────────────────────────┴────────────────────────────┘
                                  │
                                  ▼
                         [闭环检查诊断雷达 (BR-037)]
                                  │ 5项门禁全达标
                                  ▼
                            [CLOSED 已归档关闭]
```

## 四、六大核心功能模块详细设计

### 4.1 评审工作台 (Workbench)
- **功能定位**：个人高效处理入口与全局治理大盘。
- **关键设计**：
  - **待办任务聚合卡片**：
    - 待我初审的议题
    - 待我投出表决票的会议
    - 待我提交整改的缺陷项
    - 待我独立核验的整改证据
    - 待授权签发的正式决策书
  - **核心指标条**：待评审数、待表决数、严重整改项数、已归档数、SLA 达标率。
  - **流程穿透**：点击任何待办项直接定位至议题对应的工作流阶段。

### 4.2 议题管理与申报 (Topic Management)
- **功能定位**：议题全生命周期台账与流程中枢。
- **关键设计**：
  - **向导式新建议题填报 (Wizard)**：
    - 步骤 1：议题基本属性（类型、产品族、产品名、模块、期望上会日期）。
    - 步骤 2：背景、目标与本次评审核心诉求。
    - 步骤 3：影响范围（单模块/单产品/单产品族/跨产品族/企业级）与风险定级（R1-R4）。
    - 步骤 4：**智能路由测算推荐引擎**（依据影响范围与风险级别，自动推导建议层级 L1/L2/L3 与承接 DRB 组织并提供依据说明）。
    - 步骤 5：初稿技术设计说明书材料上传。
  - **申报材料快照冻结 (BR-017)**：
    - 在议题准备阶段，由组织者/秘书点击“冻结材料并启动评审”；
    - 系统计算防篡改哈希（如 `sha256:0d9f48...`），生成不可变版本（如 `v1.0-freeze`），记录冻结时间；
    - 冻结后不可替换材料，后续任何补充均以“补充附件快照”形式留痕。
  - **AI 合规预审 (AI Pre-Review)**：
    - 自动对申报文档执行红线静态度量（安全凭证 TTL、跨域 API 认证、数据一致性）；
    - 输出雷达体检得分与阻断项；
    - 专家可“一键将 AI 风险项导入为正式评审整改意见”。

### 4.3 评审会议与表决 (Meeting Console)
- **功能定位**：会前预审、会中质询与表决、会后决策移交。
- **关键设计**：
  - **审议议题切换器**：支持在会议室顶部下拉切换不同的上会议题。
  - **三模式控制台**：
    - **会前预审模式**：专家个人阅读状态登记与确认（防“不备而审”）。
    - **会中评审模式**：
      - 实时议程进度看板；
      - 现场质询快速登记并定级（P0-P3）直接沉淀为正式整改单；
      - **独立表决席位面板**：委员独立选择赞成（AGREE）、附条件赞成（CONDITIONAL）、反对（OPPOSE）、弃权（ABSTAIN）并输入个性化意见，系统实时汇总并判断是否满足法定双 2/3 门槛。
    - **会后衔接模式**：生成会议纪要，提供直通“正式决策签发”与“整改闭环看板”的跳转通道。

### 4.4 意见与整改闭环 (Comment Remediation)
- **功能定位**：严格阻断缺陷与验收闭环管控看板。
- **关键设计**：
  - **四级缺陷分类体系**：
    - **P0（阻断性缺陷）**：触犯安全红线、存在重大资损隐患或单点崩溃风险；
    - **P1（严重缺陷）**：架构设计存在高可用瓶颈或技术标准偏差；
    - **P2（一般改进）**：性能优化与规范建议；
    - **P3（微小提示）**：代码可读性与文档措辞。
  - **整改与验证双向闭环**：
    - 待整改状态：整改责任人点击“提交整改方案与证据”，录入解决方案说明与 Git PR/测试报告链接；
    - 待核验状态：独立核验人进入“独立专家审核核验”面板，查验补丁代码后点击“核验通过”或“驳回重改”；
    - 残余风险接受审批：对于无法短期消除的 P0 特殊项，须由 L1 主席/CSO 行使授权签署“残余风险接受”。

### 4.5 正式技术决策与 ADR (Decision & Architecture Decision Record)
- **功能定位**：法定裁决签署与企业级架构知识资产沉淀。
- **关键设计**：
  - **决策授权签署 (BR-026)**：
    - 由各级 DRB 主席依章程签署，包含：裁决类型（PASSED / CONDITIONAL_PASS / REJECTED）、裁决正文、强制性生效前提。
  - **ADR 自动联动与入库**：
    - 签署决策后，系统自动同步生成/更新 ADR 记录（标题、上下文、裁决理由、后续影响、状态为 `ACCEPTED`）。
  - **版本化增量修订 (BR-027)**：
    - 决策已发布后禁止修改，如需变更必须点击“发布决策新版本（修订）”，生成 V1.1 / V2.0 并留痕修订原因。

### 4.6 DRB 组织架构与授权 (DRB Org & Hierarchy)
- **功能定位**：三级治理分级授权的组织与章程基线。
- **关键设计**：
  - 树形层级交互：直观查看 L1、L2、L3 各评审委员会及横向专家组。
  - 授权矩阵：展示各级 DRB 的审批范围、表决规则与跨级上报触发器（Escalation Triggers）。
  - 委员会名单：展示现任主席、秘书长、常务委员与任期履职台账。

## 五、闭环门禁诊断雷达 (BR-037 规则引擎)

在点击“正式关闭议题”时，系统强制触发 5 项自动逻辑校验：

| 校验序号 | 门禁规则维度 | 达标判定条件 | 阻断提示 (Fail Message) |
| :---: | :--- | :--- | :--- |
| **01** | 议题受理与形式审查 | `status !== 'DRAFT' && status !== 'PENDING_ACCEPTANCE'` | 待 DRB 秘书完成形式审查与正式立项 |
| **02** | 申报材料快照冻结 | `materials.every(m => m.version.includes('freeze'))` | 申报材料尚未生成 SHA-256 不可篡改快照 |
| **03** | 评审表决法定门槛 | `ballot.passedQuorum && ballot.passedThreshold` | 实到人数或赞同率未达到双 2/3 法定多数 |
| **04** | 授权决策人签署决议 | `Boolean(decision.signatoryName && decision.publishedAt)` | 待授权 DRB 主席签署正式裁决书 |
| **05** | 严重缺陷(P0/P1)独立核验 | `unverifiedCriticalCount === 0` | 尚有未完成独立核验的 P0/P1 严重缺陷 |

当且仅当上述 5 项全部通过时，议题方允许正式执行终局关闭并归档入库。

## 六、结语

本平台通过将复杂的企业级架构治理抽象为 6 个清晰贯通的核心工作流模块，既保障了多产品族快速迭代的技术自治活力，又构建了重大架构红线刚性管控的高可靠治理防线。
